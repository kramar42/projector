# P8 — Typed facets

Status: **shipped**, types only. The expression language — moving the pseudo-facets into `facets.yaml`
— is deliberately not here; see "Deferred" below and [TODO.md](TODO.md).

---

## The idea

P7 introduces `ref: true`. That is really one value of a slot the model does not have yet: a facet
**type**.

```yaml
priority: { type: label, values: [now, month, backlog, someday], single: true }
project:  { type: ref }
due:      { type: date, single: true }
estimate: { type: number, single: true }
```

Obsidian arrived at the same place from the other direction — its Properties are typed
`text · list · number · date · checkbox`, assigned once per property name and applied vault-wide,
which is exactly what `facets.yaml` does with vocabulary. It is the strongest signal that a type slot
is the right shape, and it is further along than us on everything except references and traversal.

## Why it matters: `due` stops being special

In P6 I made `due` a top-level field, arguing a facet is a string set matched for membership while a
date needs comparison against today. **That argument only holds while facets are untyped.** A
date-typed facet knows how to compare, so `due` becomes an ordinary facet and takes several special
cases with it.

Absorbed by this change:

| today | after |
|---|---|
| `Rec.due` as a field, with its own schema entry, `KEY_ORDER` slot and `--due` flag | `facets.due`, like anything else |
| `dueBucket()` and the `due` pseudo-facet | the facet declares its own `buckets` |
| the `due` branch in the sort comparator, and the `records.due` column | one `ordered` comparison, for any date or number facet |
| `checkDue`, hardcoded to one field name | a type check inside `checkFacets`, for any typed facet |
| the `--due` flag and the panel's bespoke date field | `--facet due=…`, and a control the *type* picks |
| no range filters anywhere | `f.due=<2026-09-01` for any ordered type |
| every facet value is a string | numbers sort as numbers; an `estimate` facet becomes possible |

`created` and `updated` stay fields: they are written by the app, not vocabulary the user declares.

## Buckets, and why they are part of the type

A date facet has as many distinct values as there are dates, so a filter panel listing them is useless
and a board grouped by one gets a column per day. What you want from a date on those axes is a
*bucket* — which is exactly what `PSEUDO.due` computes by hand today.

So an ordered facet may declare its own boundaries, and that is what makes migrating `due` possible at
all: without it the `due` pseudo-facet would shadow the `due` facet by name.

```yaml
due:
  label: Due
  type: date
  single: true
  buckets: { overdue: -1, today: 0, week: 7 }   # days from today; past the last one is `later`
```

**An ordered facet presents buckets and compares raw.** Filtering and grouping see `overdue · today ·
week · later`; sorting and range filters see the date. The two are lexically distinct in a query —
`f.due=overdue` is a bucket, `f.due=>2026-09-01` is a range — so there is nothing to disambiguate.

This is not the deferred expression language sneaking in. A boundary list is part of what an ordered
type *is*; an expression is a computation the vocabulary does not otherwise describe.

## Decided

- **Type and computed-ness are independent slots**, not one enum. A computed date should sort and
  range-filter like a stored one.
- **`single` stays its own key.** It is a cardinality constraint, not a type, and it already ships.
- **`created` and `updated` stay fields.** A facet is *user-declared vocabulary*; those two are written
  by the app on every save and belong in no filter panel. That is the line, and it is why `due` can
  move and they cannot.
- **`staleness` stays a pseudo-facet**, since it is computed over `updated` — a field. Computing over
  app-written metadata is the residual role of `PSEUDO`, and a coherent one.
- **Storage stays `string[]`.** The file holds strings; the *type* governs interpretation. That is what
  keeps this small: `valuesOf` and `rankOf` are the only two places the engine reads a facet, and both
  are single functions.

## Deferred

**The expression language.** Moving the five pseudo-facets into `facets.yaml` needs one, and its
hardest case cannot be a per-record expression at all: `blocked` requires the aggregate pass that scans
every record's `blocks` references, so it needs engine-backed built-ins whatever the syntax. Designing
that against a *typed* engine is strictly easier than against an untyped one, so it waits.
