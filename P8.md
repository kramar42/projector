# P8 — Typed facets (draft)

Status: **draft**. Context capture, not a spec. Do not start this before P7 ships — it touches every
assumption P7 relies on, and mixing them makes both un-shippable.

---

## The idea

P7 introduces `ref: true`. That is really one value of a slot the model does not have yet: a facet
**type**.

```yaml
priority: { type: label, values: [now, month, backlog, someday], single: true }
project:  { type: ref }
due:      { type: date, single: true }
estimate: { type: number, single: true }
```

Obsidian arrived at the same place from the other direction — its Properties are typed
`text · list · number · date · checkbox`, assigned once per property name and applied vault-wide,
which is exactly what `facets.yaml` does with vocabulary. It is the strongest signal that a type slot
is the right shape, and it is further along than us on everything except references and traversal.

## Why it matters: `due` stops being special

In P6 I made `due` a top-level field, arguing a facet is a string set matched for membership while a
date needs comparison against today. **That argument only holds while facets are untyped.** A
date-typed facet knows how to compare, so `due` becomes an ordinary facet and takes several special
cases with it.

Absorbed by this change:

| today | after |
|---|---|
| `Rec.due` as a field, with its own schema entry, `KEY_ORDER` slot and `--due` flag | `facets.due`, like anything else |
| `dueBucket()` and the `due` pseudo-facet | a date type knows its own buckets, or a computed facet declares them |
| the `due` / `created` / `updated` / `title` branches in the sort comparator | one comparator per type |
| no range filters anywhere | `f.due=<2026-09-01` for any ordered type |
| every facet value is a string | numbers sort as numbers; an `estimate` facet becomes possible |

`created` and `updated` stay fields: they are written by the app, not vocabulary the user declares.

## Declarable computed facets

The second half, and the reason to do both at once. There are five pseudo-facets compiled into
`query.ts` — `type`, `blocked`, `triage`, `due`, `staleness`. Adding a sixth is a code change.

Bases lets a user declare one in a text field:

```yaml
formulas:
  overdue_flag: 'if(due && status != "Done", …)'
```

So: computed facets move from `PSEUDO` in `query.ts` into `facets.yaml` as expressions.

```yaml
staleness:
  type: computed
  values: [week, month, older]
  of: 'days_since(updated) <= 7 ? "week" : days_since(updated) <= 31 ? "month" : "older"'
```

C8 survives — every one is still deterministic, a count or a date comparison, never a judgement — and
the guarantee moves from "we only wrote deterministic ones" to "the expression language cannot express
anything else", which is stronger.

Companion, from the same source: **per-view summaries** (count, sum, average over a grouping), which
would generalise `projectRollups` from one hardcoded entity type to any grouping. See TODO.

## Open questions

- **What is the expression language?** It must be sandboxed, total, and cheap enough to run per record
  per query. Not JS. Probably a small expression evaluator over facet values, dates and counts — the
  five existing pseudo-facets are the acceptance test: if it cannot express `triage` and `blocked`, it
  is too small.
- **Do computed facets need a type too, or are they always `label`?** All five current ones yield
  labels. A computed *date* or *number* is plausible (`days_until_due`) and would want to sort and
  range-filter like a stored one — which argues type and computed-ness are two independent slots, not
  one enum.
- **Does `single` survive as its own key**, or become `type: label` vs `type: label[]`? Obsidian
  distinguishes Text from List that way. Ours reads better as a separate flag, but that is taste.
- **Does the histogram still make sense for ordered types?** A date facet has as many values as there
  are dates. It probably wants buckets rather than a value list — which is what the `due` pseudo-facet
  is doing by hand today, and suggests bucketing is a property of an ordered type rather than a
  separate computed facet.
- **How much does the query engine assume `string[]`?** `matches`, `histogram`, `spread`, `comparator`
  and `orderValues` all do. That is the real cost of this change and it should be measured before
  committing.
