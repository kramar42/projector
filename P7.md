# P7 — References

One relation mechanism instead of two. `edges:` becomes reference facets, `kind` goes, and the
view model loses two keys that were saying the same thing twice.

Status: **shipped**, all five steps. What follows is the record of what was decided and why; open
items moved to [TODO.md](TODO.md).

---

## The change in one page

A card model with `facets` **and** `edges` has two ways to say "this record relates to that one",
with two storage shapes, two write paths, two traversals and two sets of capabilities. Facets can be
filtered, grouped, counted, dragged and bulk-edited; edges can be traversed, cycle-checked and drawn.
Neither can do the other's job, and no record needs them to be different.

So: **a facet value is either a label or a reference**, and a reference is a record id in this vault.

```yaml
# before                              # after
---                                   ---
id: fix-deploy                        id: fix-deploy
kind: card                            title: Fix the Kpow deployment
title: Fix the Kpow deployment        facets:
facets:                                 priority: [now]
  priority: [now]                       status: [active]
  status: [active]                      project: [project-a]
  project: [project-a]                        parent: [eventing]
edges:                                  blocks: [conduktor-config]
  - {type: parent, to: eventing}      links:
  - {type: blocks, to: conduktor-config}  - jira:PROJ-303
links:                                due: 2026-09-01
  - jira:PROJ-303                     ---
due: 2026-09-01
---
```

The whole model is then three sentences:

> A record is `id · title · facets · links · body`, plus optional project config, `due` and timestamps.
>
> A facet value is either a **label** from a declared vocabulary, or a **reference** to a record in
> this vault.
>
> A **link** is a reference to something outside the vault.

Facets point inward, links point outward. That is the entire distinction, and it replaces the
facet/edge/link trichotomy that exists today.

## Why this is not just tidying

Reference facets are strictly more capable than edges, because everything the facet engine already
does starts applying to relationships:

| | today | after |
|---|---|---|
| filter by parent | impossible | `f.parent=project-a` |
| "cards with no parent" | impossible | `(none)`, like any facet |
| group a board by parent | impossible | `groupBy: [parent]` |
| drag a card between parent columns | impossible | the existing drag semantics, unchanged |
| bulk re-parent | `POST /api/bulk` op `parent`, a special case | the ordinary `facet` op |
| parent in the filter panel with counts | impossible | free |
| traverse the project facet | `memberEdges()`, synthesised per query | the same walk as every other reference |
| refuse a membership cycle | not done | the same check as `parent` |

The measured cardinality says the board and panel cases are real rather than theoretical — a hierarchy
concentrates, so its values behave like a grouping axis:

| facet | distinct values | uses | used exactly once |
|---|---|---|---|
| `project` | 11 | 138 | 0 |
| `parent` | 21 | 112 | 6 |
| `blocks` | 1 | 1 | 1 |

`blocks` is the exception and does not want to be a board axis — which is fine, because the axis worth
having there is the derived `blocked` one, and it already exists.

## `ref: true`

A new property in `facets.yaml`. It says: **the values of this facet are record ids.**

```yaml
parent:
  label: Part of
  ref: true

blocks:
  label: Blocks
  ref: true

project:
  label: Project
  ref: true
```

Semantics:

- **Values must resolve to a record.** A dangling reference is a `ck check` warning, not an error —
  same as a dangling edge today, so an agent writing a card before its target exists is not blocked.
- **`open` is implied and `values:` is rejected.** A vocabulary of record ids cannot be declared in
  advance, so declaring one is always a mistake. One fewer key to get wrong.
- **Cycles are refused.** On write, in `checkFacets`, using the existing `wouldCycle` generalised over
  a facet name. Every reference facet that exists needs this — `parent` for tree layout, `blocks` for
  dependency, `project` for config inheritance — so it is the rule, not an option. If a genuinely
  cyclic reference facet ever appears, that is when to add a knob.
- **`single`, `label` and the rest work unchanged.** A reference facet is a facet.

`valuesFrom: 'project-records'` is deleted. It existed to give one facet a vocabulary from the data;
`ref: true` says that generally. The narrower rule it also encoded — *a `project` value must name a
record carrying a `project:` block* — already lives in `validate.ts` and stays there.

### Direction

Traversal needs a direction, and the honest one is mechanical rather than spatial:

- **`out`** — follow this record's values. `parent` out is what it is part of; `blocks` out is what it
  holds up.
- **`in`** — find the records naming this one. `parent` in is what it contains; `blocks` in is what
  holds it up.
- **`both`** — the union of two separate walks, as today.

`up`/`down` is replaced because it only reads correctly for containment: on `blocks`, "up" would mean
"toward the blocker", which is the same arrow as `parent`'s "down". `out`/`in` is exact for every
facet and needs no per-facet property. The sidebar can render it as *follows* / *referenced by*.

This deletes the `Via` union and the `'member-of'` string: `via` becomes any reference facet name.

### Layout

The canvas lays out by **the first reference facet in `show`** (below). If `show` names none, there is
no hierarchy and the graph is positioned freely. This replaces the `HIERARCHY` array in `layout.ts`
and the rule that `blocks` is drawn but never fed to dagre — put `parent` first and `blocks` second
and you get exactly today's behaviour, stated in the view rather than hardcoded.

## Removing `kind`

`kind` gates three things today: which glyph draws, whether `/triage` nags for a missing project, and
`home.yaml`'s default filter. Nothing structural.

It goes, because the job it was doing is already done:

- **Off boards.** `home.yaml` filters `status: [planning, active]`. A grouping record with no status
  is excluded by that filter already. `kind: [card]` was redundant with it.
- **The glyph.** Becomes derived from whether anything references the record — which reflects what is
  true instead of asserting it.
- **The triage exemption.** There is nothing to exempt. If a container is just a card, then
  `session-identity-reliability` being `active` until its children are done is a true statement, not a
  mis-triage.

What actually distinguished a node was *no lifecycle of its own*, and absence of `status` says that
directly. Under C11 — nothing derivable is also stored — a stored flag restating the record's own
shape is exactly what should go.

Deleted: the `kind` facet, `kindOf`, the `records.kind` column, `counts()`'s cards/nodes split, and the
two-way branch in `KindMark`.

## Instructions move into the project block

`resolveProject` reads a project's instructions by regex-matching a `## Instructions` heading in the
record's **body** and taking everything until the next `##`. That is the only place in the model where
prose is load-bearing: rename the heading, or write `### Instructions`, and config inheritance silently
stops producing anything. There is no error, because there is nothing to check against.

Instructions are project configuration, so they belong with the rest of it:

```yaml
project:
  jira: SUPPORT
  branch: "kc/{card}"
  repos:
    - {path: ~/Code/work/infra, base: main}
  instructions: |
    - Never change a realm in eu-prod without a ticket and a rollback plan.
    - Realm config goes through keycloak-config-cli. Never hand-edit exported JSON.
```

The body goes back to being what C6 says it is — free-form, with no section the app reads. Inheritance
is unchanged: the strings still concatenate outermost-first so the most specific advice reads last,
and each is still tagged with the record it came from.

Deleted: `extractInstructions`, its regex, and the `## Instructions` convention from the seed README
and the skills.

Migration: for each record carrying a `project:` block, move the body's `## Instructions` section into
`project.instructions` and remove the heading. Records whose section reads `_None recorded yet._` lose
it entirely rather than inheriting a placeholder.

## View model

Two keys are saying one thing, and one key belongs to the shape.

### `chips` + `edges` → `show`

Today `chips: [project, tech]` is "which facets appear on a face" and `edges: {show: [parent, blocks]}`
is "which edge types the canvas draws". Once relationships are facets, these are one list — *which
facets does this view surface* — and how each is drawn follows from what it is:

| | label facet | reference facet |
|---|---|---|
| board / canvas face | a chip | a chip that opens the target |
| canvas | — | a line between records |
| table | a column | a column of links |

```yaml
show: [parent, project, priority, tech]
```

One key, and the answer to "why does my canvas draw nothing" becomes "there is no reference facet in
`show`" rather than a second key you forgot.

### `connect` moves to the shape

`connect: 'ancestors'` keeps unmatched ancestors so a filtered graph stays connected. `parseSpec`
already derives it from the shape and only a canvas honours it. It stops being a query key and becomes
what it is: a canvas rendering rule, following the layout facet rather than `parent` unconditionally.
That also fixes the standing bug where a `member-of` canvas pulls in context from the parent tree.

### `ViewSpec` after

```yaml
shape: board | canvas | table
title: Home
filter: { status: [planning, active], parent: [project-a] }
focus: { id: project-a, via: parent, dir: in, depth: 2 }
q: keycloak
groupBy: [priority, project]
sort: [due:asc, priority:asc]
uncategorised: end | start | hide
show: [project, tech]
nodes: { project-a: {x: 0, y: 0} }
order: { now: [id, id] }
```

`view = filter × focus × shape × facets` still holds, with one fewer key under `facets` and one fewer
under the query.

## Considered and deferred

**Unifying `focus` into `filter`.** A focus is a filter clause whose test is transitive rather than one
level deep, so in principle `filter: { parent: { values: [project-a], depth: ∞, dir: in } }` collapses two
concepts into one. It is deliberately not in this spec: the two-level split is load-bearing for the
facet panel. `focus` bounds the *universe* and `filter` refines inside it, and the panel decides which
facets to offer from the universe while counting from the filtered pool. Collapsing them changes what
"38 filtered out" means. Worth doing as its own decision, with the histogram semantics settled first.

**Whether `parent` survives at all.** After the P6 cleanup, 111 cards carry both a parent and a
project, 27 carry a project only, 1 carries a parent only. `parent` may turn out to be redundant with
`project`. That is a `facets.yaml` question, answerable by living with the clean structure — and the
point of this spec is that the mechanism no longer cares. Build references; decide which ones exist
afterwards.

**Making `links` facets.** A link kind as a facet would mean 90 cards' worth of singleton values in
the filter panel, and enrichment needs the typed string anyway. Instead, add a computed `linked` axis
(`jira`, `gh:pr`, `doc`, `slack`, `url`) so "everything with a Jira link" is askable — which it is not
today, across 90 cards that carry one. Small, and it belongs with this work.

**Typed facets — the successor, deliberately not folded in here.** `ref: true` is really one value of a
`type:` slot, and Obsidian's property system (`text · list · number · date · checkbox`) is the same
idea taken further. If a facet could declare `type: date`, then `due` would not need to be a top-level
field at all — a typed facet knows how to compare, which is the whole reason `due` was made a field in
P6. That decision is worth reopening, and it would also absorb `dueBucket`, the hardcoded date
branches in the sort comparator, and range filters (`f.due=<2026-09-01`), which no facet can express
today. It is not in P7 because it touches every assumption that a facet value is a string matched for
membership, and mixing it with references would make both un-shippable. Ship references, then type
them.

**Edge attributes.** A reference facet value is a bare id, so a relationship can never carry data of
its own. Nothing uses that today (`Edge` is `{type, to}`), and a reason for a blocker belongs in the
body. Accepted knowingly.

## CLI

### Nested setting replaces the missing verbs

There is no way to create or configure a project from the CLI today, and `ck set x --project` fails
silently because unrecognised flags are dropped. Rather than a verb per structure:

```bash
ck set project-b --set project.jira=SUPPORT
ck set project-b --set 'project.branch=kc/{card}'
ck set project-b --set 'project.repos=[{path: ~/Code/work/infra, base: main}]'
ck set mapping --set 'project={}'          # this is "make it a project"
ck set mapping --set project=              # and this is "stop being one"
```

`--set <dotted.path>=<yaml>`, where the value is parsed as YAML. One mechanism, no DSL, and it is the
CLI equivalent of `PUT /api/card/:id/frontmatter`, which already exists and already validates. It
subsumes `--title`, `--due` and `--facet`; `--add` and `--remove` stay, because those are set
operations rather than assignments.

An unrecognised flag must become an error. Silent acceptance is how the above went unnoticed.

### The other two gaps

```bash
ck rm <id>...                    # drops references to it, like the server already does
ck set <id>... --set f=v         # accept several ids, so a bulk move is one call
```

`ck` has no delete, so the only available path during the P6 cleanup was `rm`, which left a dangling
reference. And 70 single-record invocations each re-read the whole vault; the app has `POST /api/bulk`
that the CLI never got.

## Migration

One script, then delete it — the P6 pattern.

1. For each card, move every `edges: [{type: T, to: X}]` into `facets: { T: [X, …] }`, preserving
   order, and drop `edges:`.
2. Drop `kind` from `facets:`.
3. Rewrite `facets.yaml`: add `parent` and `blocks` with `ref: true`, add `ref: true` to `project`,
   drop `valuesFrom`, drop `kind`.
4. Rewrite views: `chips` + `edges.show` → `show`; drop `connect`; drop `kind` from filters; `via`
   and `dir` values updated (`member-of` → `project`, `down`/`up` → `in`/`out` per facet).
5. `ck check` must report zero errors, and `ck stats` must report the same record count.

Every write goes through `patchKey`, so comments and hand formatting survive.

`KEY_ORDER` inside `facets:` should put reference facets last, so the classification of a card reads
first and its relationships after.

## Sequencing

1. `ref: true`, generic `refsOf`, generic cycle check — the mechanism, with `project` migrated onto it
   and `parent`/`blocks` still edges. Nothing user-visible changes; the engine stops having two of
   everything.
2. `parent` and `blocks` onto reference facets. Migration. `edges:` and the `edges` table go.
3. `kind` out. `show` replaces `chips`/`edges`. `connect` moves to the shape.
4. CLI: `--set`, `ck rm`, multi-id, flag validation.
5. `linked` axis.

Steps 1 and 2 are the commitment. 3–5 are independent and can land in any order.
